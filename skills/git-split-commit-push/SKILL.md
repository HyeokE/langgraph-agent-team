# Git Split Commit Push

현재 워킹트리 변경을 하나의 커밋으로 뭉치지 말고, 리뷰 가능한 논리 단위로 나눠 커밋하고 push한다.

## 실행 절차

1. 작업 상태를 수집한다.
   - 실행: `git status --short --branch`
   - 실행: `git diff --name-status`
   - 필요 시 실행: `git diff` / `git diff --staged`
2. 커밋 경계를 먼저 설계한다.
   - 파일 단위가 아니라 변경 의도 단위로 묶는다.
   - 서로 독립 배포 가능한 변경은 별도 커밋으로 분리한다.
   - 리팩터링과 기능 변경이 섞였다면 분리한다.
   - 포맷팅 전용 변경은 기능 변경과 분리한다.
3. 각 묶음별 검증 전략을 정한다.
   - 가능한 최소 범위의 테스트/린트만 실행해 빠르게 검증한다.
   - 테스트가 없으면 정적 점검(`typecheck`, `lint`)을 우선 적용한다.
4. 묶음 단위로 스테이징하고 커밋한다.
   - 파일 선택: `git add <path...>`
   - hunk 단위 분할: `git add -p <path>`
   - 커밋 전 확인: `git diff --staged`
   - 커밋 메시지는 한 줄 요약 + 필요 시 본문(왜 필요한지)으로 작성한다.
5. push 전 최종 점검을 수행한다.
   - 실행: `git log --oneline --decorate -n <커밋수>`
   - 실행: `git status --short`
   - 예상치 못한 파일(`.env*`, 비밀키, 로컬 캐시)이 포함되지 않았는지 확인한다.
6. 원격 브랜치로 push한다.
   - 최초 push: `git push -u origin <branch>`
   - 이후 push: `git push`
7. 결과를 보고한다.
   - 커밋별 해시, 제목, 포함 파일, 수행한 검증 명령, push 대상 브랜치를 요약한다.

## 커밋 분할 기준

- 기능 추가/수정
- 리팩터링(동작 동일)
- 테스트 추가/수정
- 문서/설정 변경
- 포맷팅/기계적 변경

위 항목이 혼재하면 가능한 한 분리한다.

## 운영 규칙

- 사용자 요청 없이 `git reset --hard`, 강제 push(`--force`)를 수행하지 않는다.
- 이미 존재하는 미관련 수정사항은 되돌리지 않고 그대로 둔다.
- 충돌하거나 애매한 경계가 있으면 임의 결론 대신 분할 기준을 짧게 제시하고 진행한다.
